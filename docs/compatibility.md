# Compatibility

J++ is an experimental source transpiler for competitive programming. **It does not yet support all GNU++23 features or all compiler intrinsics.** Clang 18 determines which input syntax is accepted; Java lowering is a separate, smaller compatibility boundary.

## Known gaps

- Byte views of nested records, record fields containing arrays, pointers or references, lambda closures, unions, bitfields, and nontrivially copyable records; runtime `offsetof` indices, converting storage addresses to integers, resolving integer addresses to live storage, integer-derived function pointers, arbitrary object reinterpretation, placement construction, and complete storage layout semantics. Opaque integer pointer sentinels support retention and equality; dereference and arithmetic require additional address lowering. Allocation sizes and byte-view indices are bounded by Java's indexed storage limits. Noncanonical bool bytes and floating representations that a JVM changes when materializing a value are explicitly rejected.
- Backward and computed jumps, jumps into nested scopes, and full unstructured control flow.
- Other control contexts for `setjmp`, including loop conditions, condition declarations and initializer statements, and conditions outside a directly handled compound statement; jumps around checkpoint scopes and signal-mask checkpoint APIs. A checkpoint suffix currently rejects exits to surrounding loops and forward goto; loops and switches wholly inside the suffix retain their ordinary control flow. C++ restrictions on jumping over nontrivial automatic destruction still apply.
- Return/goto and break/continue escaping a GNU statement expression; consteval results requiring object snapshots; dynamic initialization of static data members.
- Full object lifetimes and RAII: destruction of members, arrays, containers, value parameters/results, captured objects, other full-expression temporaries, static/global objects, heap objects, and explicit destructor calls. Scoped user destructors currently require a direct block-local declaration and trivially destructed fields. Reference lifetime extension and GNU cleanup attributes need additional lowering.
- Inheritance, unions, bitfields and RTTI. Deallocation relies on Java garbage collection for supported objects without user destructors.
- Complete exceptions: nontrivial exception objects, inherited handler matching, potentially throwing destructors during unwinding, constructor/destructor function-try-blocks, converted function-pointer catches, member-pointer exceptions, implicit standard-library exceptions, exception-pointer APIs, uncaught-exception counts and custom termination handlers need additional lowering. Other guaranteed-throw initializer and condition contexts still need Java reachability lowering. Default termination exits with status 134. Mutable pointer-reference catches follow the C++ reference rule; [testing](testing.md) documents their native compiler oracle.
- Generic lambdas with multiple concrete call signatures, every capture mode, all reference-returning expressions, and full iterator/reference invalidation semantics. Set node-value merging does not yet preserve iterator identity across containers.
- Complete comparator propagation on container assignment, all heterogeneous comparator overloads, and full callable ownership when copying `std::function`. Ordinary scalar closure captures are copied independently when the Java callable signature is unchanged; borrowing through `std::ref` retains the original closure. Init captures, captured `this`, non-scalar capture copies/moves, and owning adapters between different signatures need additional lowering.
- All constructor overloads after Java type erasure, all emplacement/default-argument and reference-member cases, and complete user-defined move semantics.
- Constant/zero initialization preceding all dynamic global initialization, thread-local storage, and static initialization that observes partially constructed records.
- General named modules, user-module dependency discovery and linking, header units and `std.compat` need additional lowering. Automatic `std` setup exports available toolchain declarations; it does not implement Java lowering for every exported library API. Explicit module-file arguments must match the selected frontend and its configuration.
- Coroutines, concurrency, atomics, platform APIs, inline assembly, and target-specific SIMD intrinsics.
- Complete GNU policy based data structures: mapped trees, custom comparison and node-update policies, other tree tags, joining/splitting, node-level APIs, and other PBDS container families need additional lowering. Arbitrary third-party libraries, full ranges/views, and complete C++23 library coverage remain unfinished. Ranges still need unbounded/custom iota, 129-bit iterator differences for 128-bit values, mixed-signedness explicit views, other views/range algorithms, projections, callable destruction, and more general result conversions.
- Custom seed-sequence types, other random-engine families and adaptors, random distributions, engine stream serialization, and complete random-library coverage.
- C random streams for other target libraries, alternate state buffers with `initstate`/`setstate`, and reentrant random-state APIs need additional lowering. The implemented stream follows GNU libc's default generator.
- Floating, unsigned, narrow, and user-defined chrono representations; calendar/time-zone facilities, time-point text formatting, clock serialization, and complete chrono/thread-library coverage. Clock resolution and scheduling follow the selected JVM and operating system.
- Direct formatted input into bitsets and complete bitset constexpr object evaluation. Bitset exception paths need the general C++ exception backend.
- Complete extended floating-point support: `long double` text output, byte representations, signaling NaNs and payloads, floating-environment changes and exceptions, other extended formats, and additional mathematical functions need lowering. The implemented x87 arithmetic uses the default nearest/even environment. Locale-sensitive I/O and complete C `printf`/`scanf` compatibility also remain unfinished.
- Wide-character strings and streams, complete locale semantics, and Unix filenames that are not valid UTF-8. Narrow string sizes are limited by Java's 32-bit indexing; string exception paths need the general C++ exception backend.
- `main`'s GNU environment parameter and command-line bytes that the Java launcher cannot decode as Unicode. Java argument strings are encoded as UTF-8 in the generated C++ argument table; `argv[0]` is the generated Java class name.
- C file handles and their error indicators, complete file open-mode combinations, seeking, mixed read/write streams, and file-stream exception masks.
- Complete synchronized C/C++ I/O interleaving and terminal-specific buffering behavior. The stream synchronization flag follows the GNU library's one-way disabling behavior; it does not create native C stream buffers.
- Complete stream formatting: immediate output `setw`, `setfill`, left/right/internal alignment and output width/fill accessors are supported, including byte strings and unformatted `put`/`write`. Stored manipulators, input width, other formatting flags, locale facets and stream exception masks need additional lowering.
- Complete GMP: other integer APIs, rational/floating families, allocation callbacks and capacity observability, raw representation copying and memory access, and nonzero nail-bit configurations need additional lowering. The implemented representation-field operation is a computed `_mp_size` read; references and writes are rejected. GMP headers must be available to the C++ frontend; generated Java needs no GMP library.
- Exact unsigned `__int128` wraparound and all edge cases of C++ integer promotion and conversion rules.

Java's stack depth, boxing and collection memory overhead, and `BigInteger` costs differ from native C++. Passing a differential test is evidence for that tested behavior, not a full conformance claim or a time-limit guarantee.

Reaching the end of an ordinary non-void C++ function without returning a value has undefined behavior, apart from `main`'s implicit zero return. Translated functions retain their returning paths and raise `IllegalStateException` on supported fallthrough paths. This guard can also satisfy Java's conservative return analysis for a C++ path that cannot execute.

## Diagnostics

Most unsupported constructs produce an explicit `j++` error, for example:

```text
solution.cpp:12:5: error: j++: unsupported statement GCCAsmStmt
```

Some unsupported combinations are currently caught only by Java compiler validation. This is why `--check` is available and why new lowering paths need execution tests, not just source snapshots.
